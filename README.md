# firetable-user
client side front end for firetable, a virtual music listening room powered by firebase.

pairs with a node.js "chatbot" backend ([firetable-hostbot](https://github.com/mxew/firetable-hostbot)) that manages song lengths, queue order, DJ playcounts...

## first time setup
Steps for first time setup (running a firetable room locally) can be found [here](https://github.com/mxew/firetable-user/wiki/first-time-setup).

## configuration
- make a copy of config.js.example
- rename copy to config.js
- edit contents of config.js with your own configs/api keys

## soundcloud
**How it works today (no SoundCloud app, nothing paid), and it should stay this way:**
- Playing SoundCloud tracks uses SoundCloud's embeddable player, which needs no key.
- Pasted soundcloud.com links and playlist imports work through the legacy resolver (`SC_RESOLVE_URL` / `SC_PROXY_URL` in `js/constants.js`). Keyword search shows a message asking for a link.
- The hostbot checks each SoundCloud track before it plays with SoundCloud's own web API and a client id (`SOUNDCLOUD_KEY` in the bot's `.env`; see "soundcloud" in the firetable-hostbot README).

SoundCloud's official API only answers requests signed with a registered app's client ID *and* secret, which this room doesn't have, so `api/soundcloud.php` answers `501 not configured` and the site uses the paths above. Don't remove the legacy resolver or switch the bot over while that's the case: SoundCloud links, imports and tracks would stop working. Both workarounds rely on services SoundCloud (or the resolver's host) could change; if links stop resolving or the bot says it can't reach SoundCloud, nothing is lost (the bot flags nothing and keeps YouTube tracks playing) and the fix is a working client id, not a code change.

### adding an official SoundCloud app later (optional)
If the room gets a registered SoundCloud app (SoundCloud reviews app requests; depending on their current terms that may need a paid plan), the site and the bot are ready for it. SoundCloud's API only accepts OAuth requests, which need your app's client secret, so the browser can't search it directly. `api/soundcloud.php` (PHP 8.1+ with cURL) gets and caches the token and handles track search, playlist search, link lookups and playlist imports.
- register the app at https://soundcloud.com/you/apps and note its client ID and secret
- copy `api/soundcloud-config.php.example` to `api/soundcloud-config.php` on the server
- add your SoundCloud app's client ID and secret (or set `SOUNDCLOUD_CLIENT_ID` / `SOUNDCLOUD_CLIENT_SECRET`)
- the file is git-ignored and the deploy never uploads or overwrites it
- the proxy only answers this site's pages (plus any `allowed_origins` you list) and rate-limits each visitor IP (default 120 requests per 10 minutes, set with `rate_limit`); see the example config
- check `https://<your site>/api/soundcloud.php?action=tracks&ids=13158665` answers with JSON instead of `501`; keyword search then works
- for the bot, add the same values to its `.env` as `SOUNDCLOUD_CLIENT_ID` / `SOUNDCLOUD_CLIENT_SECRET` and restart it (firetable-hostbot README, "soundcloud")

Without it, pasted soundcloud.com links and playlist imports still work through the legacy resolver; keyword search shows a message asking for a link. Keep the legacy resolver either way: it's the fallback when the proxy can't help.

## last.fm scrobbling
Last.fm signs every scrobble with your API account's shared secret, so the browser never gets it: `api/lastfm.php` (PHP 8.1+ with cURL) adds the API key, signs the call and relays Last.fm's answer. It only signs connecting an account, now playing, scrobbles and loves.

Scrobbles follow what each listener actually hears: the room's song in Live, or the song they're playing in Discover. Time only counts while the song is really sounding (not paused, muted, buffering, held back by the browser or covered by a preview), and a song is scrobbled once half of it (or 4 minutes) has been heard, as Last.fm asks.
- easiest: add repository secrets `LASTFM_API_KEY` and `LASTFM_SECRET` (Settings → Secrets and variables → Actions) with the values from https://www.last.fm/api/accounts. The deploy writes `api/lastfm-config.php` on the server from them, readable only by your account, and checks the proxy answers afterwards
- or by hand: copy `api/lastfm-config.php.example` to `api/lastfm-config.php` on the server and fill it in (or set the `LASTFM_API_KEY` / `LASTFM_SECRET` environment variables). The deploy leaves a hand-made file alone
- the file is git-ignored, so the secret never enters git
- same caller check as the SoundCloud proxy; each visitor IP gets 60 calls per 10 minutes by default (`rate_limit`)

Without it, the "Set up Last.fm scrobbling" link and scrobbling stop working; nothing else is affected.

Both proxies share `api/common.php` (config loading, caller check, rate limit, HTTP); `api/.htaccess` keeps it and the config files from being served.

## guests and radio listeners in the people list
The people list counts everyone with the room, not just the members in it: its header shows the total (beside a crowd icon), then members, **guests** (visitors on the site without an account) and **radio listeners**, each beside its icon and named on hover (a count of none is left out, and so is its group below), and under the members, **On the radio** lists the stream's listeners merged by country (a flag, the country and how many; "Somewhere" for listeners it can't place) and **Guests** has how many visitors without an account are here, by country in the same rows, then a 🎧 **Listening live** row for how many of them hear the room. Visitors see the same under who's in the room, and the room pulse adds "N on the radio". The Turntable theme's People shows them too.

The members themselves are `js/people.js`: the DJs first, in deck order under **On the decks** (who's playing, who's next, each one's plays this turn in words, "2 plays" or "1 of 3" when the bot sets a limit, with a tooltip that says so, and who steps down after their next play; a DJ's card, the tooltips on the stage's DJ name and on-deck faces, and the Turntable theme's seats and DJ menu say it the same way, `firetable.people.plays`, where they said "1/∞"), then everyone else by name under **On the floor**. Every face has a dot (green here, orange away), an idle row says for how long from five minutes on, your own row says "you", and whoever fired the song that's on has a flame until the next one.
- `api/audience.php` (PHP 8.1+ with cURL, sharing `api/common.php`) answers with counts only. Guests' pages send it a heartbeat once a minute (a random id made in the browser, so tabs count once, and whether the room is sounding), and say goodbye when they close or sign in; a guest counts for 2½ minutes after their last one. Ids are kept under a keyed hash for those minutes only, with no address (only a keyed hash of one, so a single address can add at most 6 guests). Robots (by user agent, and `navigator.webdriver`) and pages nobody is looking at or hearing aren't counted. A guest's country comes from their device's time zone (`Europe/Berlin` is Germany), which the server places with PHP's own time zone data (ICU's, through PHP's intl, where the server has it, which also knows older names like `Asia/Calcutta`): no address is looked up anywhere, only the country is kept, and a zone with no country (UTC, `Etc/…`) is "Somewhere". Members' pages only ask, while they're visible.
- The stream comes from Broadcast Pal's `api/listeners.php` ([id-broadcast-pal](https://github.com/indiediscotheque/id-broadcast-pal), "Listener cities and the time check"), which already reads Icecast with its admin login, drops bots and looks up where each listener is. `api/audience.php` asks it at most once a minute and passes on countries and counts only (never cities). Set the repository variable `BROADCAST_PAL_URL` (Settings → Secrets and variables → Actions → Variables) to Broadcast Pal's page, e.g. `https://example.com/broadcastpal/`, and the deploy writes `api/audience-config.php` from it (or copy `api/audience-config.php.example` by hand; `LISTENERS_URL` in the environment works too). Without it, guests are still counted and the radio rows stay hidden.
- After a deploy, "Check the people list's counts" in the workflow log says what the server sees: guests, radio listeners and countries.

## chat lines
The chat keeps its last 50 messages whatever their age, so a heading goes in where the day changes ("Yesterday", "Today", "Monday, Nov 23"). The bot's line that someone fired the song has a flame before it (the mark the people list gives them), a command typed to the bot ("!skip") is set as quietly as the bot's own lines, and the names the bot quotes in backticks keep their colour without the typewriter face. Times are in the chat's own type. All of it is `js/chat-lines.js`, called by `js/chat.js` as each message is drawn.

## the stage with nobody playing
With nobody playing (no song, or the bot's own stand-in for none, `cid` 0), the stage's song card says **Nothing playing**, with what played last under it when that's known ("Last played: Night Drive · Glider": the song that just ended, or the newest of the room's Recent plays once they've loaded) and the room's own art (`defaultAlbumArtUrl`, else `img/idlogo.png`), and no plays, tempo or clocks (on a phone the words take the width a DJ would stand in, and "The decks are open" has a row of its own under them; the Turntable theme's room keeps that note across its stage): before, a first visit to a quiet room kept a grey "Loading firetable…" skeleton, and an emptied room kept the last song. The player bar says the same ("Nothing playing · The room is quiet"), and so does the Turntable theme's songboard. Its words are plain then (Discover's links on the song's title and artist come back with the next song), and the room's own players stop: a preview that ends or is stopped in a quiet room stops with it, coming back to the tab doesn't start the last song again, and a SoundCloud song's screen goes as a video's does. That and the decks' own note ("The decks are open") are `js/stage-state.js`.

## hostbot
Works with the original bot ([mxew/firetable-hostbot](https://github.com/mxew/firetable-hostbot)): the site only uses bot commands and database paths it already has. A few extras need [indiediscotheque/firetable-hostbot](https://github.com/indiediscotheque/firetable-hostbot): `!lights` / `!lightson` / `!lightsoff` outside the lights months, seasonal trading-card avatars, the autopilot DJ (the bot plays whenever the decks are empty), and timing stamped with the database clock (with the original bot, song positions follow the bot server's clock).

### play history (first plays and play counts)
The "first … by …" / "last … by …" lines and the play count under the song come from the bot (`tagUpdate`). With the indiediscotheque hostbot's play history published (`tools/history` in that repo), they cover every copy and spelling of a song back to the room's first play, the count is the room's own, and "· N all versions" appears when remixes and live versions have been played too. A play the history knows the date of but not the DJ shows no "by". Tag fixes made here are logged in `tagLog` with the fix, so the history trusts them over other spellings. That needs the hostbot's current `firebase-rules.json`; with older rules the fix is saved without the log entry.

### seasons stay in sync with the bot
Seasonal settings live only on this site: defaults in `js/seasons.js`, overrides in `config.js` (`avatarset`, `avatarSeasons`, `lightsMonths`, `snowMonths`). The indiediscotheque hostbot reads both files from the live site, at startup and every 10 minutes, so its trading-card avatars and `!lights` replies follow them. Change them here, deploy (or edit `config.js` on the server), and the bot picks it up with nothing to change on the bot. It needs `SITE_URL` (this site's address) in the bot's `.env`. The bot reads these settings with a parser and never runs the files, so keep them plain values (text, numbers, `true`/`false`, lists and objects), not expressions or function calls; anything else is skipped.

## errors and speed from real visits
`js/telemetry.js` (loaded right after `config.js`, before the site's own scripts) reports two things straight to the database, with `navigator.sendBeacon` to its REST address (no sign-in, no library):
- **errors in the site's own scripts** (`clientErrors`): the message, the file with its `?v=` version, line and column, a short stack, the page (the first parts of its address only), the browser's family and version, and whether someone's signed in. At most 5 a visit, each once. Other sites' scripts (the players, browser add-ons) are left out, and so are fetches the site stops on purpose.
- **how fast the visit felt** (`clientVitals`), once, the first time the page is hidden or closed: largest paint, the slowest response to a tap, click or key, the worst burst of layout shift, first paint and server response (Google's Web Vitals), Live or Discover, phone or computer.

No user id, name or IP address goes with them. Anyone can add a report; only the bot and supermods can read them, and the bot deletes them after two weeks (firetable-hostbot's `firebase-rules.json` and README, "site health"). Every Monday the hostbot's **Site health** workflow groups them and writes a report on its run's page, with each error's line in the source; it fails, so GitHub emails, when an error is in a script that's still live or a vital is poor over 20 or more visits.

The deploy minifies the scripts (below) and gives each a **source map** beside it (`js/chat.js.map`, not in git; `tools/minify.mjs --maps`), so the browser's tools show the readable source, and the Site health report can say which line an error is on.

## analytics
Google Analytics (GA4) counts visits: `js/analytics.js`, loaded with `async` from the `<head>` of `index.html` (and so the library's plain pages), `about/`, `privacy/` and `terms/`. It's Google's tag as a file, because the security policy runs no inline scripts. Not on the embeds, which show inside other sites.
- **The measurement IDs** are on that `<script>`, in `data-id` (several with a space between: each stream gets the same visits). Change them in all four pages; `tests/analytics.test.mjs` fails when the pages differ.
- **Only on the live site:** nothing loads from `localhost` or `127.0.0.1`, so development and the browser tests are never counted.
- **Global Privacy Control:** a browser that sends it never fetches Google's script. `privacy/` says so.
- **Private addresses:** with a one-time `?token=` (the way back from Last.fm) the page is reported with only its campaign parameters (`utm_…`, `gclid`).
- **Pages within the site** (Live to a library page and back, `history.pushState`) are counted by the stream's Enhanced measurement ("Page changes based on browser history events", on by default).
- **The policy** in `.htaccess` allows the tag's folder (`https://www.googletagmanager.com/gtag/`) in `script-src` and where it reports in `connect-src`. If the browser's console shows Google blocked there after a setting changes in Analytics, add that host.

## database costs
The Realtime Database bills every byte it sends, to every browser, so the site asks for as little as it can:
- **Playlist tracks are saved lean.** A YouTube track doesn't keep its thumbnail or watch page; both are built from its id wherever they're shown (`ftapi.utilities.leanTrack`, the same rules as the hostbot's `lib/tracks.js`). Your open playlist downloads on every visit, so every track counts.
- **Playlist counts:** each list's length is counted on load (every track's key, but never the tracks). Coming back to the tab later fetches only the flagged counts again: playing from a list moves a track, it doesn't add or take one away.
- **Grab stats** in Profile come from the hostbot's sum (`grabCount/<uid>`), not every grab you've ever had; until the hostbot keeps that sum, the site counts them itself.
- **Typing:** "is typing" writes your name once and then only refreshes the time, at most every 5 s; an entry older than 11 s is ignored.
- **Discover** follows its live data (new releases, the week's chart) only while it's open. **The live stage for other sites** reads the hostbot's small `stage` summary, never `users/`.

## checks
`npm ci && npm run lint` runs ESLint on `js/` (the config lists the globals each script shares). GitHub Actions runs it, plus a PHP syntax check of `api/`, on every pull request and before every deploy. None of these tooling files are deployed.

**Size budget:** `node tools/size-budget.mjs` adds up what the home page downloads from this site before anyone does anything (its own scripts, stylesheets, preloaded fonts and emoji data, and the page), minified and gzipped as the deploy serves it, and fails over the limits in `tools/size-budget.json`. Lint runs it on every pull request. Over it: load the new part on first use (`js/lazy.js`, as the Turntable theme does), or raise the budget in the same pull request and say why (`--write` sets today's sizes plus 5%).

**jQuery only shrinks:** new code uses the browser's own DOM, and code that's being changed anyway drops its jQuery as it goes (CLAUDE.md, "jQuery"). `node tools/jquery-budget.mjs` counts each script's jQuery against `tools/jquery-baseline.json` and fails when one uses more, or uses less without the baseline being lowered too (`--write`). Lint runs it on every pull request.

**File and function size:** ESLint's `max-lines`: 500 lines of code a file and 80 a function, comments and blank lines not counted. The files already over keep today's size as their own cap, and their number of long functions too (`tools/line-limits.json`); `node tools/line-limits.mjs` (lint) fails when either grows, or shrinks without the record being lowered (`--write`). New features go in files of their own (CLAUDE.md, "File size").

`tests/` holds the browser tests (`.github/workflows/smoke.yml`, on every pull request; reach runs as one job per role). Each serves the site under the real Content-Security-Policy from `.htaccess` (`tests/harness.mjs`) and loads it in Chromium:
- **unit** (`unit.test.mjs`, `npm run unit`): the site's own functions as the page loads them: escaping, the chat formatter (markup people type never becomes elements), links and inline images, database keys, usernames, tracks, avatars and dates. With it, `analytics.test.mjs`: the Google Analytics tag is on every page and no embed, loads nothing from the tests' address or for a browser sending Global Privacy Control, and on a stand-in for the live site runs under the policy (Google's hosts are stood in for, so no visit is counted).
- **smoke** (`smoke.mjs`, `npm run smoke`): the site against a local database emulator. Fails on page errors or anything the policy blocks, and checks the song and theme show, YouTube's player loads, the stage effects load on first use, the service worker receives a push, and much more.
- **screens** (`screens.mjs`, `npm run screens`, not in CI): the redesign's before and after pictures. Real accounts (a member, the DJ on deck, a mod) and a visitor, at 390, 1024, 1440 and 1920 wide, in each Live tab, each Discover page, the full-screen player, a Discover song carried into Live, a full stage with a waitlist and an empty one. Pictures go to `tests/screens/<short sha>/` (not committed) with an `index.html` contact sheet; `BASE=<an earlier sha>` compares pixel by pixel, putting the earlier picture and a diff beside each one that changed; two runs of the same code match (clocks and times masked, the video hidden, avatars and covers cached in `tests/screens/.cache`). `ROLES`, `WIDTHS` and `VIEWS` narrow a run. The data is `seed.mjs`, the same the smoke test starts from.
- **reach** (`reach.mjs`, `npm run reach`), "nothing lost": about 70 features from the redesign's inventory, each with the controls a person taps to reach it, checked as a visitor, a member, the DJ on deck and a supermod at 390, 1024 and 1440 wide. Fails when a control is gone, hidden, covered, or shows for a role it shouldn't. A change that moves a control updates its route in the same pull request.
- **a11y** (`a11y.mjs`, `npm run a11y`): [axe-core](https://github.com/dequelabs/axe-core) (pinned) for names, labels, roles and structure, and a contrast check of every piece of text against what's behind it (WCAG AA), in each main view as a visitor, a member and a supermod at 390 and 1440 wide. Fails on a serious or critical finding not in its allowlist, which holds what the site has today with the step that fixes each and only shrinks. Also fails on text under 10px (the type floor, 1.2), and when an icon's word is read as part of a control's name ("Hop on queue_music": Material Symbols icons are words the font draws as pictures), for every button, link and menu item in the page, open or not, whether the icon is in the markup or drawn by the stylesheet (a `::before` or `::after`): an icon inside one is `aria-hidden="true"`, and a control that is only an icon has an `aria-label`.
- **avatars** (`avatars.mjs`, `npm run avatars`, no emulator): every avatar style in every place it's drawn (the people list, chat, the header, on deck, Discover's faces and its big one, the stage at the room's size and scaled up, the embedded stage), photographed and measured: each fills its circle and sits in the middle, and stands on the table filling the stage. Writes a contact sheet to `tests/screens/avatars.png`.
- **rules** (`rules.mjs`, `npm run rules`): real accounts in the auth emulator (a member and a mod) use the site's own actions (chat, reactions, playlists, preferences, profile, grabs, blocks, log out, mod tools) against the hostbot's real `firebase-rules.json`, and it fails on any read or write the rules refuse, then checks each write landed. CI uses the rules on the hostbot's `master`; locally set `HOSTBOT_RULES` or keep a `firetable-hostbot` checkout next to this repo.

Run them with `cd tests && npm ci && npx playwright install chromium`, then `npm run unit`, `npm run smoke`, `npm run reach`, `npm run a11y`, `npm run avatars` and `npm run rules` (Java 21 needed for the emulators). On `master` they run as part of the deploy, which only publishes if they pass; each suite gets a second try first, since they load the CDNs and YouTube. If a CDN is down, a manual run of the deploy can skip them ("Skip the browser tests").

## deploy
Every push to `master` publishes the site to DreamHost (pages last, so a visitor mid-upload never gets a new page before its scripts) (`.github/workflows/deploy.yml`, settings listed at the top of that file). It runs the checks below first and only publishes if they pass. The `?v=…` on each link to this site's own scripts, stylesheets and fonts is set at deploy time from a hash of that file, so visitors' browsers fetch exactly the files that changed; there's nothing to bump by hand (except `config.js?v=`, since `config.js` lives only on the server). Because each link changes with its file, `.htaccess` lets browsers keep those hashed files for a year (`Cache-Control: immutable`; not `config.js` or `sw.js`). The repository secret `DREAMHOST_KNOWN_HOSTS` (the output of `ssh-keyscan <your DreamHost server>`, run on your own computer) is required: the deploy only logs in to that server. It logs in with `DREAMHOST_PASSWORD`, or, if the repository secret `DREAMHOST_SSH_KEY` holds a private key whose public half is in the user's `~/.ssh/authorized_keys`, with that key only (no password is ever sent then).

## social posting
`.github/workflows/social.yml` runs every hour (`tools/social/`). The room's bot starts it at 17 minutes past each hour ([firetable-hostbot](https://github.com/indiediscotheque/firetable-hostbot), README "social posting", with its `SOCIAL_GITHUB_TOKEN`), since GitHub's own schedules run late or get skipped. The workflow's schedule stays on as a backup; an extra run finds nothing new to post. It works out what's due, draws it, puts the files on the site under `social/` and posts them, keeping to each platform's budget. The research behind the formats, the budgets, the keywords and the design is in the social audit (linked from the pull request that added it).

**The week** (the room's time zone, the `TZ` repository variable, default `America/Chicago`). Weekly posts go out on weekday mornings, when the feeds are busiest; the day's song goes out in the evening, when the video apps are:

| kind | when | what |
|---|---|---|
| `chart` | Monday 9:00 | last week's top 10: a carousel and a countdown video |
| `rising` | Wednesday 9:00 | the songs played more these four weeks than the four before |
| `newweek` | Friday 9:00 | New Music Friday: the week's new releases, the ones the room played most first |
| `fires` | Saturday 11:00 | the week's most-fired song |
| `spotlight` | daily 18:00 | one new release the room has been playing, or, on a day without one, the song first played here on this day in an earlier year (`onthisday`) |
| `wrapped` | December 1st | the year's top 10 and the room's year in numbers |
| `theme` | when it happens | a new room theme, and a recap when one ends |
| `busy` | 8 or more people online, at most once a day | "N listening right now", as Stories |

Posts name songs and artists, never the room's DJs.

**Hands-off by default, and people hear the songs.** Nothing needs a person once the keys are set. No audio is ever uploaded: the song plays from the platforms' own licensed sources.
- **Instagram:** the daily song is a Reel with the song from Instagram's own music library, attached through its Audio API when the library has that exact song. It goes out as a Trial Reel (`INSTAGRAM_TRIAL`), shown to non-followers first and shared with followers if it does well. When the library doesn't have the song, its picture is posted instead. This needs Instagram through Facebook Login (below). Turning on "Share your reels to Facebook" in Instagram's Accounts Center puts the Reels on the Page too.
- **Everywhere else** a song post carries the song's own YouTube video, the upload the room plays it from. Facebook and Bluesky show it as a card that plays in the post; Discord and Telegram play the link inline; Threads and Mastodon link it ("▶ Hear it"). Every play counts for the artist's upload.
- **Carousels and pictures** (charts, New Music Friday, Rising, Wrapped, themes, Stories) post themselves.

**Optional extras that take a few minutes a day** (left out unless their secrets are set):
- **TikTok:** the video arrives in the app's inbox as a draft; add the sound from TikTok's picker and post. TikTok offers no way to add music from outside the app.
- **The post kit** (`STUDIO_DISCORD_WEBHOOK` and/or `STUDIO_TELEGRAM_CHAT_ID`): one message to a private channel each day, with the video and the Story picture to save, the song to pick and each caption to paste. It covers YouTube Shorts, Facebook Reels and Stories with a music sticker, which have no way to add licensed music from outside the apps. It also covers Instagram Reels whose song isn't in the API's library (with the kit set up, those wait for the kit instead of posting the picture).

**One post per song.** A song gets a single post of its own a year. That holds whichever kind it comes up in (new release, the room's favourite, On This Day) and whichever upload it was played from. Lists (the chart, New Music Friday) can name it again. "(feat. …)", "(Official Video)", case and accents don't make a new song; a remix, edit or version does. Every post also has its own id that's never sent twice, a post that fails is retried only on the platforms that failed, and the workflow stops rather than start from nothing when it can't read what's been posted.

**Budgets** (`tools/social/run.mjs`, `SOCIAL_BUDGET` to change one, e.g. `threads=3/15/3`; `pinterest=0` turns one off). Bluesky and Discord have none: every post goes to both. A post over budget skips that platform, and one over budget everywhere waits for another day:

| | a day | a week | hours apart |
|---|---|---|---|
| Instagram feed (Reels, carousels) | 1 | 5 | 20 |
| Instagram Stories | 2 | 10 | 4 |
| Facebook feed / Stories | 1 / 1 | 4 / 7 | 20 / 8 |
| TikTok drafts, the post kit | 1 | 5–6 | 20 |
| Threads, Mastodon | 2 | 10 | 3–4 |
| Bluesky, Discord | every post | | |
| Telegram | 2 | 12 | 3 |
| Pinterest | 2 | 10 | 3 |

**Words built for each platform's search and ranking** (`captions.mjs`, `keywords.mjs`):
- **The opening line** names the genre, artist and song people search for ("French house new release: Justice, …"). The genre is the room's own, or the artist's most played genre here for songs not tagged yet.
- **Under it:** a fact from the room (plays, chart moves), "sounds like" artists, and a prompt to comment, save or send. Those are what the feeds rank on.
- **Tags:** CamelCase hashtags, which screen readers read as words. Instagram and TikTok get 5 (Instagram's cap), YouTube #Shorts and 2 more, Threads one topic, Bluesky 3, Mastodon 4, Pinterest none (it ranks on keywords).
- **Links:** Instagram and TikTok say "link in bio". YouTube and Pinterest titles are keyword titles ("Justice - Starting From Zero (New French House 2026)").
- **Alt text** on every picture where the platform takes it.
- **UTM tags** on every link, so the site's stats show what each platform sends.

**Artists:** their accounts come from MusicBrainz (exact name matches only). They're @-mentioned and invited as Instagram collaborators (`INSTAGRAM_COLLAB=false` turns that off).

**Design** (`render.mjs`):
- **One left edge:** everything hangs from it, so every post reads as one series. The room's mark with the post's subject sits at the top, then the album cover, the song, the artist and a line of facts, then the address alone at the foot. The record slides out of the sleeve to the right and runs off the edge.
- **The ground** is the room's near-black, lit by the song's own colour with a little grain. The cover and its colour are what change from post to post.
- **Three layouts:** 4:5 for feeds; 9:16 for videos, with everything between y 290 and 1250 and left of x 930, clear of the Reels, TikTok and Shorts buttons and captions and inside Instagram's 3:4 grid crop; 9:16 for Stories, which only need about 250 px clear at the top and bottom, so the cover and type are larger.
- **Song videos** run 30 seconds and loop seamlessly (the record makes whole turns).
- **Carousels** open on a hook (the number one, or the covers), then one song a slide (each stands alone, since Instagram can re-show a carousel from slide 2), then a "listen live" slide. Platforms that take 4 pictures get the hook and the list, five songs a slide.

**Setting up** (repository secrets; a platform is left out until its secrets are set; `node tools/social/run.mjs platforms` lists what's set and each budget):

| platform | secrets | how |
|---|---|---|
| Facebook Page and Instagram (with music) | `FACEBOOK_PAGE_ID`, `FACEBOOK_PAGE_TOKEN`, `INSTAGRAM_USER_ID`, `INSTAGRAM_TOKEN`, and the variable `INSTAGRAM_GRAPH_HOST=graph.facebook.com` | an Instagram professional account linked to the Facebook Page, a Meta app with Facebook Login for Business, then `node tools/social/auth.mjs facebook` (prints them all; the tokens don't expire) |
| Instagram without Facebook | `INSTAGRAM_TOKEN` | `node tools/social/auth.mjs instagram`. No music: songs go out as pictures |
| Threads | `THREADS_TOKEN`, `THREADS_USER_ID` | the Meta app with the Threads use case, then `node tools/social/auth.mjs threads` |
| TikTok (optional: drafts to finish in the app) | `TIKTOK_CLIENT_KEY`, `TIKTOK_CLIENT_SECRET`, `TIKTOK_REFRESH_TOKEN` | an app at developers.tiktok.com with Login Kit and the Content Posting API (`video.upload`), then `node tools/social/auth.mjs tiktok` |
| the post kit (optional) | `STUDIO_DISCORD_WEBHOOK` and/or `STUDIO_TELEGRAM_CHAT_ID` | a webhook on a private Discord channel; or message the Telegram bot and use your chat id |
| Bluesky | `BLUESKY_HANDLE`, `BLUESKY_APP_PASSWORD` | Settings → Privacy and security → App passwords |
| Mastodon | `MASTODON_URL`, `MASTODON_TOKEN` | Preferences → Development → New application (`write:statuses write:media`). Tick "This is an automated account"; a server's bot rules (a tag, a daily limit) go in `SOCIAL_MASTODON_TAGS` and `SOCIAL_BUDGET` |
| Pinterest | `PINTEREST_APP_ID`, `PINTEREST_APP_SECRET`, `PINTEREST_REFRESH_TOKEN`, `PINTEREST_BOARD_ID` | an app at developers.pinterest.com, then `node tools/social/auth.mjs pinterest` |
| Telegram channel | `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | a bot from @BotFather, made an admin of the channel (`@channelname`) |
| Discord | `DISCORD_WEBHOOK_URL` | the channel → Edit → Integrations → Webhooks |

`auth.mjs` needs the app's id and secret in the environment (named at the top of the file) and the app's redirect address set to `https://www.indiediscotheque.com/` (or `REDIRECT_URI`). It prints a link; allow the app and paste back the address the browser lands on. `SOCIAL_SKIP` leaves a kind out on a platform (`fresh:x`); by default nothing is skipped.

**When a platform refuses:** a 401, 402 or 403 (keys refused, no API credits, no permission) fails that post on that platform at once, as an error on the run's page saying what to fix, instead of being tried twice more. A post that didn't go out gives its place in the budget back, so the next one isn't held back. Addresses in the log have their secrets masked (a Discord webhook's token, a Telegram bot's).

**Trying it:** Actions → "Social posting" → Run workflow. "Dry run" (on by default) draws what's due and prints every platform's words and the post kit without uploading or posting; pick a kind and "Post even if it isn't due" to send one now. Locally, `node tools/social/run.mjs preview --site https://www.indiediscotheque.com/ --kind spotlight,chart --out /tmp/social` draws them and prints everything (needs ffmpeg for the videos).

**Where the files go:** Instagram, Facebook and Threads fetch each post's pictures and videos from a public address. DreamHost's firewall refuses Meta's servers some of the time, so the files go on GitHub Pages instead: the `social-media` branch, served at `https://indiediscotheque.github.io/firetable-user/social/`. The workflow replaces that branch on each run (one commit, no history), keeping only the files from the last 10 days and any still waiting to post, and waits until Pages serves them before posting. The branch also carries copies of the privacy policy and terms (`…/firetable-user/privacy/` and `…/terms/`), which Meta can always read: use them in the Meta app's settings. Turn Pages on once, after the first run has made the branch: **Settings → Pages → Build and deployment → Deploy from a branch → `social-media`, `/ (root)` → Save**. To go back to the site's `social/` folder, set the repository variable `SOCIAL_MEDIA_HOST=site`.

**What it keeps:** `firetable-social/state.json` in the SFTP user's home on the server (outside the site, never served). It holds what's been posted and where, the queue, the past week's posts (for the budgets), renewed tokens and 30 days of lookups. Until a platform has its keys, runs draw nothing; the first run after that counts every new release already out as posted, except the newest 3.

## security headers
`.htaccess` sends a Content Security Policy plus the usual hardening headers (no framing by other sites, HSTS, nosniff, referrer and permissions policies). The policy allows no inline scripts or event handlers, so add new behavior in the `js/` files with `addEventListener` / jQuery `.on()`, not `onclick="…"`. If you load something from a new host, add it to the matching directive in `.htaccess`. The policy only covers firetable's own paths, so other sites in folders on the same server (such as `/basement`) keep working; when you add a top-level file or folder, add it to the list in the `<If>` above the policy (CI checks this).

The deploy never overwrites the server's `.htaccess`: it puts this file inside a `# BEGIN firetable` … `# END firetable` block at the top and keeps every other rule (DreamHost's, redirects, anything added by hand). The previous copy is saved as `.htaccess.firetable-previous`. If the site answers with a server error afterwards, the old file is restored and the run fails. Set the repository variable `SITE_URL` if the site's address isn't the last part of `DREAMHOST_PATH`.

## fonts
Inter is the site's type, numbers, times and dates included, with equal-width digits (`font-variant-numeric: tabular-nums`) where they stand in a column; they were Roboto Mono until November 25, 2026 (Round 5). Roboto Mono (`--font-numbers`) is for code and keys (code in chat, the shortcuts list, the embed code, and the Turntable theme's own look), so a visit fetches it only when one of those is on screen. Inter, Roboto Mono and Open Sans are self-hosted variable fonts, each split in two by `tools/subset-fonts.py` (`pip install fonttools brotli`): `fonts/<name>.main.woff2` holds Latin plus every character the site's own text uses, `.rest.woff2` the rest, and `css/fonts-local.css` (written by the tool) gives each a `unicode-range`, so browsers fetch the second part only for text that needs it (e.g. Cyrillic in a chat message). The full originals are in `tools/fonts/` (not deployed). After adding text with new characters to the site, run the tool again. The icons are `fonts/material-symbols-outlined.woff2` (`tools/subset-icons.py`).

## third-party libraries
Loaded only when needed: SoundCloud's player (`#sc-widget`) gets its address the first time a SoundCloud track plays (`firetable.media.scLoad` in `js/player.js`), so visits that never play one don't load it. There's no jQuery UI: dragging rows to reorder them is `firetable.utilities.dragSort` (`js/helpers.js`; mouse, touch and pen, plus Alt+arrow keys in the room's playlist), and the stage's volume is a native range input. The idle timer is `idleTracker` in `js/state.js`.

CDN scripts are pinned to exact versions and checked with Subresource Integrity: most in `index.html`, and the album-art glitch's p5.js (SoundCloud songs) in `js/lazy.js`, which loads it the first time the effect shows instead of with every page. The fire needs no library: `js/flame.js` draws it on a plain canvas, for the site and the live stage alike. The Content-Security-Policy in `.htaccess` allows each of these exact files, not whole CDNs. When upgrading one, update its URL in the policy and its `integrity` hash:
`curl -sL <url> | openssl dgst -sha384 -binary | openssl base64 -A`

## older iPads (Safari 15.4 and up)
iPads that stop at iPadOS 15 or 16 (iPad Air 2, iPad mini 4, iPad 5th and 6th generation, the first iPad Pros) run Safari 15 or 16. The site works there because:
- **Popover:** Safari added the `popover` attribute in 17, and without it every menu shows in the page and the first tap on one throws. `js/popover-polyfill.js` (a copy of [@oddbird/popover-polyfill](https://github.com/oddbird/popover-polyfill) 0.7.3, BSD-3-Clause) adds it where it's missing and does nothing elsewhere; it also makes `matches(":popover-open")` and `querySelector(":popover-open")` work. Its styles are in `css/looks.css` (`@supports not selector(:popover-open)`), because the security policy blocks the `<style>` it would inject before Safari 16.4. An open polyfilled popover has the class `:popover-open`, so CSS that styles open popovers needs `.\:popover-open` beside `:popover-open`, in a separate rule.
- **CSS nesting:** Safari reads it from 16.5. The deploy serves the stylesheets flattened (`tools/flatten-css.mjs`, postcss-nesting), so the source keeps its nesting; CI checks they flatten (`node tools/flatten-css.mjs --check`).
- **Minified, not newer:** the deploy then minifies every script and stylesheet in place (`tools/minify.mjs`, esbuild, about 40% less to download). Each file stays its own file with its globals' names, and nothing newer than Safari 15.4 reads is introduced. CI runs the smoke test on that build too ("smoke (as deployed)").
- **Storage:** `js/storage.js` keeps the app going when `localStorage` is blocked or full (Safari gives a site about 5 MB): a write that doesn't fit lasts the visit instead of throwing.

`tests/smoke.mjs` loads the site with popover taken away and `:popover-open` refused as a selector, as on those iPads, and with every storage write refused. Colours made with `color-mix()` and container units need Safari 16; on iPadOS 15 those few touches fall back to plainer colours and sizes.

## light mode
The site is dark; light mode is a choice for everyone, visitors too, kept on the device (`firetableLook`: `light`, or `auto` to follow the device's own light or dark setting; nothing stored means dark). Ways to switch: the sun (or moon) in the header (a visitor's: a member's is in the account menu, with About, at every width), **Light mode** in the account menu (a switch; the menu stays open), **Settings → Playback and display → Look** (Dark, Light, Match this device), the `L` key, and `/light`, `/dark` or `/auto` in chat (said only to you). Another tab of the site follows at once.

- **How it works, and what it costs to load:** nothing extra. The light palette is in the stylesheets the page loads anyway (about 3 KB of tokens before compression; no second stylesheet to wait for). The one script that must run before the first paint, `js/head.js`, holds both pre-paint jobs, the iPhone viewport and light mode, in one small request kept for a year by its `?v=` hash. It puts `data-look="light"` on `<html>` and sets the `color-scheme` and `theme-color` metas (they come before it in `<head>`), so even the blank page the browser shows before the stylesheets arrive is the right colour (dark visitors no longer see a white flash there either), and the header's sun or moon is picked by CSS, right from the first paint. The switch cross-fades the whole page (a view transition), not each element at its own speed, and not with reduced motion.
- **The palette:** the "Light mode" section near the top of `css/looks.css`. Warm paper rather than cold white: a cream page, panels and rows rising to white, wells (a text box, the crate's filter) a shade darker than their panel, and the gold deepened to a bronze (`#845a02`) that reads as words on the page and carries white words as a fill. Every colour the rules once wrote out (white at some opacity, a black shadow, a scrim) is a token there whose dark value is exactly what it was, so the dark site is unchanged. A few touches are light mode's own: tooltips turn round (dark notes on the page), the select bar in the crate turns round too, chat and names are a weight heavier (dark words on light read thinner), dialogs are the brightest paper, the player bar is white with the song's colour deepened enough to read, and the `:id:` logo is inked.
- **What stays dark:** the stage (the song's colours, the screen, the DJs on their name plates, the strip under it) and the full-screen player are the room's media, a lit stage in a bright room; they keep the dark palette (`:is(#stage, #pv-full)` gets it back). So do the see-through discs over a cover's corner in Discover (⋮ and save on Home's lead song, and with a mouse on Home's and New's small covers): a saved song's mark on one keeps the dark look's gold (`#cc9933`), as the bronze would vanish into the disc. The Turntable theme is never drawn light: `head.js` takes `data-look` off while it's on, and its bar has no sun. The offline page stays dark (it's cached alone, with no scripts).
- **Checks:** `tests/a11y.mjs` measures every view's text contrast in both looks (WCAG AA, against the page's gradient at its worst for each look), and `tests/smoke.mjs` turns it on and off every way there is. `LOOK=light node screens.mjs` takes the screenshot harness's pictures in light mode.

## the left column as a toolbar
On a computer (1024px wide and up) the left column folds into a narrow toolbar, for anyone who wants more room in the middle: the button at the column's bottom right, the `[` key, or **Settings → Playback and display → Fold the left column into a toolbar**. Everyone starts with it open; the choice is kept on the device (`firetableRail`) and another open tab follows at once. The same button (folded, at the toolbar's bottom, just above your account), the key, or **Open the column** in the account menu opens it again.

- **The toolbar, in three groups,** each icon with a tooltip:
  - **Where you are, and the room:** Discover | Live (the page you're on marked at the edge, Live's red dot), in Discover the room's theme (lit when there is one; the tooltip names it: in Live it's on the stage, over the song), and in Live who's here with the count (the tooltip says who that is: members, guests, radio).
  - **In Live, the decks:** the DJs as faces (the one playing ringed in the room's colour, presence dots, faded when away; the tooltip gives the name and what the people list says: playing now, next, plays this turn, the role), the waitlist with each place in line, and Hop on. Everyone else is behind the count, so the toolbar stays short. A face opens their card as before. **In Discover:** search and the views.
  - **At the bottom:** search, mentions (with its count), community, the button that opens the column, and your account (or Join). A member's light mode, About and the shortcuts are in the account menu, as they are with the column open (at every width a member's header keeps to the theme, search, community, mentions and you; in Live on a computer the theme is on the stage); Open the column joins them while it's folded. So the toolbar keeps to what's used all the time. Visitors have no account menu, so their light mode and About stay on the toolbar.
- **A moment's peek:** who's here (the count, or a visitor's faces) and search (the magnifier, or `/`) open the column whole over the middle without moving anything under it. Escape (the focus goes back where it was), a click or the focus going outside, or choosing one of Discover's views puts it away. While it shows, the toolbar's button is a collapse button at the column's bottom right, as when the column is open: a press puts it back to the toolbar.
- **The middle, wider:** chat keeps its width and the middle takes the room the column gave up (in a visitor's Live, where the stage and the welcome keep their size, it goes to Fresh). The stage may grow to 38% of the screen's height instead of a third, so it keeps its shape instead of turning into a thin band, and the DJs and the video grow with it. When the middle is wide enough (66rem and up: about 1600px screens and wider) Live's middle becomes a **desk**: the stage across the top, your playlist down the left at full height, and the room's Recent, Fresh or Cards beside it under their tabs. Each side is about as wide as the middle is with the column open, the width their rows and cards are made for. Playlists' tab steps aside there (the playlist is always showing; with it picked, Recent is the other side), and the playlist doesn't fade when the other side's tab changes. Narrower, it's one panel under the tabs, as with the column open.
- **How it works, and what it costs to load:** nothing until it's used. `js/rail.js` and `css/rail.css` load the first time it's folded (`js/lazy.js` holds the button, the key and the switch until then); on a device where it was left folded, `js/head.js` puts `html.rail` and the stylesheet on before the first paint (`blocking="render"`, so it paints folded), and the script loads with the page. The words behind each icon stay in the page for screen readers. The column fades into its new shape (not with reduced motion), and nothing on the page stops taking presses while it does.
- **Never on phones or tablets, and never in the Turntable theme**, which has its own layout: folded or not, it looks exactly the same (its button, the toolbar's and Settings' switch aren't there, and `[` does nothing).
- **Checks:** `tests/rail.test.mjs` (in `npm run unit`), the `TB-11` rows of `tests/reach.mjs`, the `rail-*` views of `tests/a11y.mjs`. `RAIL=1 node screens.mjs` takes the screenshot harness's pictures folded.

## turntable theme (an easter egg)
Live can wear the look of Turntable.fm (`js/ttskin.js`, `css/ttskin.css`). The ways in, in Live: type `/turntable` (or `/tt`) in chat, the Konami code (↑ ↑ ↓ ↓ ← → ← → B A), or click the `:id:` logo three times. **Back to Live** in the bar (or the same again) leaves it. The choice is kept on the device (`firetableTurntable`); it's Live's alone, so Discover looks as always and the theme comes back with Live. Nothing of it downloads until someone goes in: its script and stylesheet load the first time (`js/lazy.js` stands in for it until then), or with the page on a device where it was left on.

- **It's a skin, not another room.** Every control is the room's own: Awesome is Fire, Storm takes your fire back (counts never go below none), Grab is the heart on the songboard (point at it, or tap it on a phone), along with the playlist picker and the song's link. The room's player is never moved in the page, only placed over the left screen, so going in and out never stops or reloads the music.
- **The room:** the stage, the theme over it, the awesome meter (how much of the room has fired), lights that come on as the fires add up, the LED songboard with the time left, the DJs behind their laptops with their plays, a Play Music seat when there's room, and everyone else on the floor, each in a place of their own that stays put. Everyone is drawn as Turntable drew them and deepcut.fm still does: a head picture on a body picture, each at its own place, so only the whole head moves and the body stays put. The DJ playing bobs their head on the song's beat (as Live's DJ does), people who fire rock their heads side to side, a DJ who fires small-rocks theirs (Turntable's bob, rock and smallrock, as CSS at its 20 frames a second), and an art track's cover fills the right screen (a cover inside flat bars, found from a small copy of the picture). Point at a DJ's laptop (or tap the DJ) for their menu, as Turntable had: @ Mention, their card, their DJ page; mods also Skip their song, Step them down after this song and Remove DJ, and supermods Make or Remove moderator and Suspend (the room's own actions, each for who may). Click anyone on the floor for their card.
- **Sound held back:** when the browser waits for a tap before playing, Live's Listen live is a plain Turntable button on the stage's base between the front speakers, at the stage's scale (no banner). Live's own is untouched.
- **Avatars:** every one of the 627 is unlocked (25, a photo, was taken out: someone who picked it stands as their classic). A member picks theirs the first time in (Turntable avatar in the account menu changes it), kept at `users/<uid>/ttAvatar`. Only Turntable faces show in the theme (chat, lists, the bar), and Live never shows one. Someone who hasn't picked stands as a classic chosen from their id.
- **#EVE:** in the theme the room's bot (the hostbot, jarvis) presents as **#EVE**, with avatar 3, the redhead girl, whatever its name or pick (`EVE` in `js/ttskin.js`, known by the `hostbot` flag). Its name and face change wherever the theme draws them (the table, the floor, People here, chat, its own "started playing" lines); Live never shows it.
- **Laptop stickers:** Laptop stickers in the account menu, or Stickers on your seat: a lid colour and up to ten stickers (the room's, Turntable's gold ones and its logo, and emoji) dragged about the lid (off its edge too: the lid cuts them off), turned by dragging the picked one's corner, and sized (keys too: arrows, `[` `]`, `-` `+`, Delete), kept at `users/<uid>/ttLaptop`.
- **The panel:** Queue · Room · Chat, or two sidebars (the bar's button; Queue on the left, as Turntable had it). Room has the room's welcome, People here (DJs, Moderators, Bots, Audience), Recently played, Fresh and Cards. Each tab shows its own page and nothing else, with the room above it on a phone too; there the tab bar's Library is a member's Queue tab (a visitor's is their crate, in Discover) and Live the room, and Discover's Fresh tile and its Recent plays' See every play in Live open the Room's Fresh and Recently played. The Queue tab starts with the stage's playlist picker, **You DJ from** and its headphones beside it, over the crate's own (which keeps the column's width for its name: the DJ switch is its glyph, and Shuffle is in the playlist's ⋮).
- **Light:** the stylesheet is added to the page the first time someone goes in (its address waits in a `<meta name="tt-css">` so the deploy versions it), so neither it, its font nor any picture is downloaded before. Each avatar is one WebP holding its front picture (for the faces) and each side's head and body (`img/tt/av/`, about 10 KB); only the people in the room are loaded. The picker loads a page of 16 as one picture (`img/tt/pick/`). The stickers that aren't emoji are one picture.
- **The database:** `users/<uid>/ttAvatar` and `ttLaptop` need the hostbot's latest `firebase-rules.json` published; until then they're kept on the device only, and the room sees everyone else's picks as their classic.
- **Rebuilding the art:** `tools/tt-avatars.py` (avatars and the picker's pages: each side's head and body placed as Turntable's own dance sprites in the archive have them, else as deepcut.fm's avatar data does) and `tools/tt-art.py` (the room and the sticker picture) from clones of the archive; each says how at its top.
