# firetable-user
client side front end for firetable, a virtual music listening room powered by firebase.

pairs with a node.js "chatbot" backend ([firetable-hostbot](https://github.com/mxew/firetable-hostbot)) that manages song lengths, queue order, DJ playcounts...

## first time setup
Steps for first time setup (running a firetable room locally) can be found [here](https://github.com/mxew/firetable-user/wiki/first-time-setup).

## configuration
- make a copy of config.js.example
- rename copy to config.js
- edit contents of config.js with your own configs/api keys

## soundcloud
**How it works today (no SoundCloud app, nothing paid), and it should stay this way:**
- Playing SoundCloud tracks uses SoundCloud's embeddable player, which needs no key.
- Pasted soundcloud.com links and playlist imports work through the legacy resolver (`SC_RESOLVE_URL` / `SC_PROXY_URL` in `js/constants.js`). Keyword search shows a message asking for a link.
- The hostbot checks each SoundCloud track before it plays with SoundCloud's own web API and a client id (`SOUNDCLOUD_KEY` in the bot's `.env`; see "soundcloud" in the firetable-hostbot README).

SoundCloud's official API only answers requests signed with a registered app's client ID *and* secret, which this room doesn't have, so `api/soundcloud.php` answers `501 not configured` and the site uses the paths above. Don't remove the legacy resolver or switch the bot over while that's the case: SoundCloud links, imports and tracks would stop working. Both workarounds rely on services SoundCloud (or the resolver's host) could change; if links stop resolving or the bot says it can't reach SoundCloud, nothing is lost (the bot flags nothing and keeps YouTube tracks playing) and the fix is a working client id, not a code change.

### adding an official SoundCloud app later (optional)
If the room gets a registered SoundCloud app (SoundCloud reviews app requests; depending on their current terms that may need a paid plan), the site and the bot are ready for it. SoundCloud's API only accepts OAuth requests, which need your app's client secret, so the browser can't search it directly. `api/soundcloud.php` (PHP 8.1+ with cURL) gets and caches the token and handles track search, playlist search, link lookups and playlist imports.
- register the app at https://soundcloud.com/you/apps and note its client ID and secret
- copy `api/soundcloud-config.php.example` to `api/soundcloud-config.php` on the server
- add your SoundCloud app's client ID and secret (or set `SOUNDCLOUD_CLIENT_ID` / `SOUNDCLOUD_CLIENT_SECRET`)
- the file is git-ignored and the deploy never uploads or overwrites it
- the proxy only answers this site's pages (plus any `allowed_origins` you list) and rate-limits each visitor IP (default 120 requests per 10 minutes, set with `rate_limit`); see the example config
- check `https://<your site>/api/soundcloud.php?action=tracks&ids=13158665` answers with JSON instead of `501`; keyword search then works
- for the bot, add the same values to its `.env` as `SOUNDCLOUD_CLIENT_ID` / `SOUNDCLOUD_CLIENT_SECRET` and restart it (firetable-hostbot README, "soundcloud")

Without it, pasted soundcloud.com links and playlist imports still work through the legacy resolver; keyword search shows a message asking for a link. Keep the legacy resolver either way: it's the fallback when the proxy can't help.

## last.fm scrobbling
Last.fm signs every scrobble with your API account's shared secret, so the browser never gets it: `api/lastfm.php` (PHP 8.1+ with cURL) adds the API key, signs the call and relays Last.fm's answer. It only signs connecting an account, now playing, scrobbles and loves.
- easiest: add repository secrets `LASTFM_API_KEY` and `LASTFM_SECRET` (Settings → Secrets and variables → Actions) with the values from https://www.last.fm/api/accounts. The deploy writes `api/lastfm-config.php` on the server from them, readable only by your account, and checks the proxy answers afterwards
- or by hand: copy `api/lastfm-config.php.example` to `api/lastfm-config.php` on the server and fill it in (or set the `LASTFM_API_KEY` / `LASTFM_SECRET` environment variables). The deploy leaves a hand-made file alone
- the file is git-ignored, so the secret never enters git
- same caller check as the SoundCloud proxy; each visitor IP gets 60 calls per 10 minutes by default (`rate_limit`)

Without it, the "Set up Last.fm scrobbling" link and scrobbling stop working; nothing else is affected.

Both proxies share `api/common.php` (config loading, caller check, rate limit, HTTP); `api/.htaccess` keeps it and the config files from being served.

## hostbot
Works with the original bot ([mxew/firetable-hostbot](https://github.com/mxew/firetable-hostbot)): the site only uses bot commands and database paths it already has. A few extras need [indiediscotheque/firetable-hostbot](https://github.com/indiediscotheque/firetable-hostbot): `!lights` / `!lightson` / `!lightsoff` outside the lights months, seasonal trading-card avatars, the autopilot DJ (the bot plays whenever the decks are empty), and timing stamped with the database clock (with the original bot, song positions follow the bot server's clock).

### play history (first plays and play counts)
The "first … by …" / "last … by …" lines and the play count under the song come from the bot (`tagUpdate`). With the indiediscotheque hostbot's play history published (`tools/history` in that repo), they cover every copy and spelling of a song back to the room's first play, the count is the room's own, and "· N all versions" appears when remixes and live versions have been played too. A play the history knows the date of but not the DJ shows no "by". Tag fixes made here are logged in `tagLog` with the fix, so the history trusts them over other spellings. That needs the hostbot's current `firebase-rules.json`; with older rules the fix is saved without the log entry.

### seasons stay in sync with the bot
Seasonal settings live only on this site: defaults in `js/seasons.js`, overrides in `config.js` (`avatarset`, `avatarSeasons`, `lightsMonths`, `snowMonths`). The indiediscotheque hostbot reads both files from the live site, at startup and every 10 minutes, so its trading-card avatars and `!lights` replies follow them. Change them here, deploy (or edit `config.js` on the server), and the bot picks it up with nothing to change on the bot. It needs `SITE_URL` (this site's address) in the bot's `.env`. The bot reads these settings with a parser and never runs the files, so keep them plain values (text, numbers, `true`/`false`, lists and objects), not expressions or function calls; anything else is skipped.

## discover
The library side of the site, off unless `config.js` sets `discover: true`. A Discover / Live switch sits under the room theme. Visitors open the site on Discover and members on Live, and each person's last choice is remembered.
- **Discover** shows the library in the middle (Home, New, Charts, Genres, DJs, Years, Recent plays) on the same cards and rows as Fresh and Recent. Its songs play whole, through the room's own players (like previews, so they're never scrobbled). Going back to Live, or **Listen in**, picks the room up where it is now.
- **The player bar** runs along the bottom of Discover (`#dMini`), as in other music players, and always says what you're hearing: **Discover** (gold, with the list and "3 of 18"; pause, previous / next, reload, drag through the song) or the room **● Live** (a red LIVE badge; the big button stops listening, since the room can't be paused or skipped through). While something sounds, the bar's edge, progress and label take the colour of the song's artwork, read from the cover; grey or unreadable art keeps the room's accent. **On air** means the room is playing but you've stopped it, or the browser held its sound back: press play to listen in. The other source is always one tap away on the right (the room's cover with **Listen in**, or **Back to it** for your paused pick). While the bar shows the room, the stage's own **Fire**, **Grab**, **Link**, **Skip** (your own song) and **Mod tools** buttons move into it, so each person has exactly what their role allows on the stage; visitors get Save to the crate and Join to fire. A Discover song has **Save**, **Play it in the room** (members: first in the playlist they DJ from, with Undo, and Hop on the decks when they aren't on them; visitors: join), Open and ⋮. Volume and the **full-screen player** button sit at the right. Members can DJ from Discover while they dig or play a list: when their song is next, and when it starts, a toast says so with **Listen in**, but Discover never switches what they hear by itself. Space plays or pauses (or stops and starts the room), Shift + ← / → move through the list, and the phone's lock screen and media keys follow whichever is playing. On phones it's one row (cover, song, keep, play); tapping it opens the full-screen player.
- **The full-screen player** (`#pv-full`) is made to be left on a TV, a projector or a second monitor. The bar's cover or ⤢ button opens it (or **F**), and in Live the stage's full-screen button does; it grows out of the bar (or the stage) and shrinks back into it. It shows the `:id:` mark, the room's name and theme, and the song in full: cover, title, artist, genre, year, source and tempo, **Found by** with who played it first and when, plays, last play, Rising, and a row of bars that rise and fall with the song's tempo (the room's from `songBpm`, a Discover song's from `bpm/`) in the colour of its artwork, over the cover softly blown up behind everything. **Audio | Video** (or **V**) switches between that and the song's video filling the screen behind the same words (the room's own player, moved into place by CSS; the choice is remembered). Beside the song, what's going on: for a Discover song, "Playing from" the list, Up next and the room in one row with **Listen in**; for the room, who's on the decks and next (an open spot with **Hop on**, or **Join to DJ** for visitors; **Step down** or **Leave the line** for yourself), **Just played** (plays in Discover) and the chat as it happens, with **Back to it** for a paused pick. Along the bottom: the song's time (counting down), then everything each person may do: a Discover song has previous, play / pause, next, reload, seek, Save, Play it in the room, Open and ⋮; for the room, the stage's own **Fire**, **Grab**, **Link**, **Skip** (your own song) and **Mod tools** move in (visitors get Join to fire and Save to the crate), with reload and, in Live, the big button muting the room. **Chat** opens the room's own chat beside the song (members; the chat to read and Join for visitors). **Fill the screen** makes it the browser's full screen; the screen is kept awake while it's open; the controls and cursor rest after a few seconds without a touch (the song, the room and the `:id:` stay). Escape closes the chat, then the player; Space plays, pauses or mutes.
- **The right column** goes with the player: **Playlists** for members (switch the playlist on screen, DJ from it, filter it, drag to reorder, Top / Bottom / Remove with Undo, Play or Shuffle it here, broken songs and Next marked, and Hop on the decks) or the **Crate** for visitors (play, shuffle, move up, remove), and **Chat** (the room's own chat for members; the chat to read, and Join, for visitors).
- **The library:** Home adds Rising (played more in the last four weeks than the four before), the room's genres, and On this day. Charts show each song's genre and can be narrowed to one. **Genres** has a sound map (across: band-made to machine-made; up: faster) and a page for each genre with Room favorites, New here, Deep cuts, songs by year, who plays it, the genres next door, a genre radio, and a link to the genre's playlist on YouTube Music once the bot has made it (the hostbot's README, "genre playlists on YouTube Music"; `discover/ytm`). **DJs** lists everyone with 25+ plays, each with a page: their sound, most played, brought here first, similar DJs, usual night and recent sets. Every artist name opens the artist's page, every robot its DJ's page, and the ⋮ on a song has the rest. In Live, a member's user card links to their DJ page. **Years** has each year playlist: what was played most and finds not played here yet.
- **Visitors** save songs to a crate kept in their browser. The third save offers to keep it. Joining or logging in opens the sign-in dialog over the page (see "accounts"), so they stay where they are. When they join (Google or email), the crate becomes the playlist "My Discover crate", and their DJ playlist if they have none yet. **Step inside** shows Live as visitors see it today, with the chat to read above Fresh, and tabs over the join form for what joining opens: Playlists (what they're for), Recent (the room's last plays, ready to play in Discover or save to the crate) and Cards (the latest printed).
- **Members** see their playlists in the right column, and a **Chat** tab beside it: the room's own chat, moved over (on phones, Chat in the nav opens it). While they're on another tab, new messages are counted on it. Songs saved from Discover show "Discover" in the playlist. Settings has "Show my name on public pages", which hides their name from charts, new releases and the visitors' chat.
- **Theme nights:** every night played under a room theme, with its songs in order, its DJs and fires, ready to play again (the bot saves the theme with each play from November 2026). DJ pages name the theme of each recent set.
- **Search** (the box at the top of Discover, the header's search button, or `/`): artists, genres, DJs, theme nights and songs from the room's own library as you type; members can also search YouTube (Enter), each result showing how often the room has played it.
- **Charts** show weeks on the chart, each song's fires (never counted), and a New releases filter. **Share** gives a link, a 1080 × 1350 image of the chart, or code to put it on another site (`/embed/chart/?period=week`, always the latest; `&id=2026-W46` for one week; `&rows=20`). The embed reads only the public chart and is the one part of the site other sites may frame.
- **The player** names the source (YouTube or SoundCloud) and can reload a stalled song. **Save all** puts a whole genre, DJ, artist, year or theme night list in a new playlist (or a visitor's crate). Members can join the waitlist from their playlist in Discover, and DJ pages show the trading cards they hold, and their **fires earned**: the room's `!hot` fires on their plays since November 2026, their most-fired songs and their place among DJs (DJs can be sorted by fires too; the bot's `discover/fires`, rebuilt daily). Members pick up to 6 to feature first on their own page (Feature, on a card in their card case, or Change on their DJ page); a card they give away drops off. Needs the bot's latest `firebase-rules.json` (`users/<uid>/featured`).
- **Every name is a door:** in Live, artist names in Recent, Fresh and on the stage link to their Discover pages, and a DJ's robot in Recent and Fresh opens their DJ page. A song's title, anywhere in Live or Discover, opens its **song sheet**: cover, artist and genre links, tempo, source, the room's plays, who played it first and last, how many versions have played, and Play, Save, Open and Copy link. Live's rows are drawn as before; Discover only adds the links.
- **Settings → Previews play over the room:** a 30-second preview plays in a second player with the room turned down to a fifth underneath, instead of stopping the room. Off unless chosen; SoundCloud previews still stop the room.
- Addresses: `#discover/themes[/<id>]`, `#discover/search/<words>`, `#discover`, `#discover/new`, `#discover/charts`, `#discover/charts/week/2026-W45`, `#discover/genres`, `#discover/genres/nu-disco`, `#discover/djs`, `#discover/djs/<name>`, `#discover/years`, `#discover/years/2026`, `#discover/artist/<name>`, `#discover/recent`, `#live`.

**Library pages for search engines:** the deploy gives the library real addresses under `/music/` (`tools/plain-pages.mjs`): every genre, every DJ with a page, the 500 most played artists, every year and every chart, plus `/music/sitemap.xml`, which the deploy adds to the server's `robots.txt`. Each one is the site itself with that page's songs already in Discover's middle column, so search engines read the songs, and someone arriving from a search lands in the real site: it starts on the same Discover page (the address becomes `/#discover/...`) and takes over. They're rebuilt every Monday after the bot's Play history job, and pages no longer built (a DJ who hides their name) are removed. To try it locally: `node tools/plain-pages.mjs --site https://www.indiediscotheque.com/ --out /tmp/music`.

It reads `discover/` (room charts, new releases with release dates, the chat for visitors), published by the [indiediscotheque hostbot](https://github.com/indiediscotheque/firetable-hostbot) (its README, "discover"), and `discover/lib/` (genres, DJs, artists, years, Rising, On this day), published by the hostbot's weekly Play history job (its `tools/history/README.md`, "Discover's library"), plus the play history and tempos already in the database. That needs the bot's latest `firebase-rules.json` published. To offer Google sign-in, turn it on in the Firebase console and add `signInProviders: ["google"]` to `config.js`.

## accounts
- **Join / Log in** sits in the header on every page for anyone signed out (it says Log in on a device that has signed in before). It opens the sign-in dialog over whatever's showing: Discover, Live, or the plain room. Every other "Join" and "Log in" on the site opens the same dialog (`firetable.ui.openAuth` in `js/users.js`; the one form, `#login`, moves into `#joinBox` and goes back after). Create account and Log in are tabs, with Google / Apple above them where `config.js` turns them on, and Forgot your password. A successful sign-in says hello; logging out says so.
- **Your account:** the header avatar opens a menu: Profile, Account and sign-in, Settings, Mod tools (supermods), Get the app, Log out.
- **Profile:** your avatar and name, the date you joined, change your username (Enter or Change), and your grabs.
- **Account:** your email and how you sign in; for email accounts, change your password (with the current one, or a reset link by email) and change your email (a link goes to the new address, and it changes when it's opened); Log out.
- **Settings**, grouped: @mentions (badoop, desktop and push notifications), Chat, Playback and display, Privacy, Last.fm.

## push notifications
Members can get @mentions as notifications on their phone, even with the app closed: install the site as an app (iPhone/iPad: Share → Add to Home Screen, which they need for notifications; Android: Install app), then **Settings → Push @mentions to this device**. It works in desktop browsers too.
- The [indiediscotheque hostbot](https://github.com/indiediscotheque/firetable-hostbot) sends them (its README, "push notifications"); it makes its own keys and publishes the public one as `pushKey`, so there's nothing to configure here. Until a bot with push is running, the setting says it isn't set up yet.
- `sw.js` (the service worker, at the site's root) shows each notification; tapping one opens the room's @ inbox. The app icon shows the unread count where the phone supports it. It has no fetch handler, so it never caches pages or changes how the site loads, and `.htaccess` sends it with `Cache-Control: no-cache` so updates reach phones on their next visit.
- `js/push.js` signs the device up and saves it under `pushSubs/<uid>/` for the bot, and re-checks on every visit (a subscription the browser replaced, a new bot key, or notifications blocked in the phone's settings are all picked up). Signing out removes the device; signing back in with the same account restores it.
- Options: "Also push @everyone announcements" (from mods and the bot), "Send a test" (goes through the bot, like a real mention), and the list of the account's devices with a button to remove each. The @ inbox suggests turning it on when it's opened in the installed app or on a phone.
- Nobody is pushed while they're looking at the room; the bot also skips blocked people and stale messages.
- **Get the app** (`js/install.js`): a guide to installing the site, with the steps for the visitor's own device first (iPhone/iPad, Android, computer) and a one-tap **Install the app** button where the browser offers one (Chrome, Edge, Samsung Internet). It opens from the "Get the app" card at the top of Settings, "Get the app on your phone" on the login screen (phones), and the push setting's and @ inbox's hints. Inside the installed app it says so instead.

## swap suggestions
Broken tracks get a one-tap fix when there's a working copy. Every night the [indiediscotheque hostbot](https://github.com/indiediscotheque/firetable-hostbot) (its README, "swap suggestions") looks up the flagged tracks in everyone's lists: YouTube Music audio tracks only (never music videos or "Official Audio" uploads), or, for a list kept to YouTube videos, the artist's own videos only (never audio tracks). It checks each match plays here and saves it with the track as `swap`. It looks in the room's history, the year playlists and YouTube's searches first, with no API key or quota. A paid search (`SWAP_API_UNITS` a day, 1,000 by default) is used only when the free searches stop answering.
- **⇄ on the track** (`js/playlist.js`) opens a card with the match (artwork, artist, title, album, length; "Audio track, not a video", or "The artist's video" in a list kept to videos): **Swap**, **Preview**, **Open** on YouTube Music (YouTube for videos), or **Not this one** (not suggested again for that track). On narrow rows it's in the ⋮ menu too.
- **Swap all** in the bar over the list swaps every suggestion in the playlist on screen (a second tap confirms). **Show them** filters the list to its broken tracks.
- Swapping keeps the track's place and tags, clears the flag, and saves where it came from (`swappedFrom`); the toast's **Undo** puts it back. Each track is its own small write, so a list edited meanwhile is never overwritten.
- **All Playlists** (the button by the playlist picker) is one table: each list's name (click to rename) over its track, flagged and swap counts, what it's kept to, ★ Default and 🎧 DJ from, Open, and a ⋮ menu for Rename, Check for broken tracks and Delete. Find a playlist filters by name (reordering waits until the box is cleared); select several, or all shown, to delete them together; type a name and Create for a new list.
- The playlist picker and All Playlists show how many swaps are ready; the bot's notice ("Show me") opens the list's broken tracks.
- Clearing a flag (by hand, or when the checker finds the track plays again) clears its suggestion.
- **What a list is kept to:** in All Playlists each list can be set to **YouTube Music**, **YouTube videos** or **SoundCloud** (or left at **Any source**), saved in `playlistPrefs/<uid>/format/<listID>` (`js/playlists.js`). A SoundCloud list takes SoundCloud tracks only and a YouTube Music or videos list YouTube tracks only: adding from search, Grab or a Recent row says so instead. Opening a list points Find tracks at its source. The bot's swaps follow it: YouTube Music and Any source lists get YouTube Music audio tracks, a list of videos gets the artist's videos (never audio tracks), and SoundCloud lists are skipped. Needs the hostbot's current `firebase-rules.json`; with older rules the setting doesn't save.

## checks
`npm ci && npm run lint` runs ESLint on `js/` (the config lists the globals each script shares). GitHub Actions runs it, plus a PHP syntax check of `api/`, on every push and pull request, and before every deploy. None of these tooling files are deployed.

`tests/` holds a browser smoke test (`.github/workflows/smoke.yml`, every push and pull request): it serves the site under the real Content-Security-Policy from `.htaccess`, points it at a local database emulator, loads it in Chromium, and fails on page errors or anything the policy blocks. It also checks the song and theme show, YouTube's player loads, the stage effects load on first use, and the service worker registers and receives a push message. Run it with `cd tests && npm ci && npx playwright install chromium && npm run smoke` (Java 21 needed for the emulator). It doesn't gate the deploy, since it loads the CDNs and YouTube.

## deploy
Every push to `master` publishes the site to DreamHost (pages last, so a visitor mid-upload never gets a new page before its scripts) (`.github/workflows/deploy.yml`, settings listed at the top of that file). It runs the checks below first and only publishes if they pass. The `?v=…` on each link to this site's own scripts, stylesheets and fonts is set at deploy time from a hash of that file, so visitors' browsers fetch exactly the files that changed; there's nothing to bump by hand (except `config.js?v=`, since `config.js` lives only on the server). Add the repository secret `DREAMHOST_KNOWN_HOSTS` (the output of `ssh-keyscan <your DreamHost server>`, run on your own computer) so the deploy only sends the SFTP password to that server; until then each run warns.

## security headers
`.htaccess` sends a Content Security Policy plus the usual hardening headers (no framing by other sites, HSTS, nosniff, referrer and permissions policies). The policy allows no inline scripts or event handlers, so add new behavior in the `js/` files with `addEventListener` / jQuery `.on()`, not `onclick="…"`. If you load something from a new host, add it to the matching directive in `.htaccess`. The policy only covers firetable's own paths, so other sites in folders on the same server (such as `/basement`) keep working; when you add a top-level file or folder, add it to the list in the `<If>` above the policy (CI checks this).

The deploy never overwrites the server's `.htaccess`: it puts this file inside a `# BEGIN firetable` … `# END firetable` block at the top and keeps every other rule (DreamHost's, redirects, anything added by hand). The previous copy is saved as `.htaccess.firetable-previous`. If the site answers with a server error afterwards, the old file is restored and the run fails. Set the repository variable `SITE_URL` if the site's address isn't the last part of `DREAMHOST_PATH`.

## third-party libraries
CDN scripts are pinned to exact versions and checked with Subresource Integrity: most in `index.html`, and the stage effects' libraries (PixiJS and GSAP for the fire, p5.js for the SoundCloud album-art glitch) in `js/lazy.js`, which loads them the first time the effect shows instead of with every page. The Content-Security-Policy in `.htaccess` allows each of these exact files, not whole CDNs. When upgrading one, update its URL in the policy and its `integrity` hash:
`curl -sL <url> | openssl dgst -sha384 -binary | openssl base64 -A`

## icons
`fonts/material-symbols-outlined.woff2` holds only the icons the site uses (about 260 KB instead of ~4 MB). After using an icon the site hasn't used before, rebuild it:

The full font lives in `tools/fonts/` (never deployed).

## avatars
Robot avatars provided by [robohash.org](https://robohash.org/).
